# Roadmap: V0 to V3

Each rung ships and demos on its own. The ordering is deliberate and inverting
it is how these projects die: **verifiable client, then secrecy, then
anonymity, then coercion mitigation.**

The reason for that order: client verifiability is the thing we uniquely have
(VISION.md section 3), and every later rung's cryptography is worthless
without it -- encrypting a ballot the client already misread proves nothing.

Facts below were verified in July 2026; sources at the end. Re-check the
load-bearing numbers before depending on them, per ic-git ROADMAP.md
discipline.

## Verified IC primitives

**vetKD / vetKeys -- PRODUCTION, since June 2025.** Better than assumed; no
need to design around a test key. Re-verified 2026-07-26; details below.

- Production key `Bls12_381_G2:key_1` generated by NNS proposal **137075** on
  the fiduciary subnet `pzp6e` (2025-06-20), backed up to the Internet
  Identity subnet `uzr34` via proposals 137123 / 137130 / 137131 (2025-06-26,
  ~15 min planned downtime), enabled for public canister use 2025-06-27. The
  cycle-cost table still names `pzp6e` (34-node fiduciary) as the key's home
  as of this check, and no post-2025 rotation or incident surfaced.
- Management canister API, exact shape:

  ```
  vetkd_public_key : (record {
    canister_id : opt canister_id;
    context     : blob;
    key_id      : record { curve : vetkd_curve; name : text };
  }) -> (record { public_key : blob });

  vetkd_derive_key : (record {
    input                : blob;
    context              : blob;
    transport_public_key : blob;
    key_id               : record { curve : vetkd_curve; name : text };
  }) -> (record { encrypted_key : blob });
  ```

  Only curve `bls12_381_g2`. Key names: `test_key_1` (local + mainnet),
  `key_1` (mainnet only).
- Libraries: `dfinity/vetkeys` -- `@dfinity/vetkeys` v0.4.0 (frontend),
  `ic-vetkeys` on crates.io and mops (backend).
- **Cycle cost -- now verified** (was the open item here):
  `vetkd_public_key` is **free**. `vetkd_derive_key` costs
  **26,153,846,153 cycles (~$0.0357) with `key_1`** and 10,000,000,000
  (~$0.0137) with `test_key_1`. The fee is set by the subnet holding the key,
  not the caller's subnet, so the 34-node fiduciary rate applies wherever the
  poll canister lives. Unused cycles are refunded; the docs advise sending
  more than the advertised amount.
- **The cost worry this line used to carry was misplaced, and the reason
  matters for the design.** Derivations are **O(1) per election, not
  O(voters)**, in the IBE shape: voters encrypt to the election identity under
  a master public key that costs nothing to fetch, and a key is derived only
  at close, once per decryptor. A 5,000-member co-op election costs about four
  cents in derivations. It becomes O(voters) only if the design gives each
  voter a personally derived key -- which is a real fork (it buys "only you
  can re-open your own ballot") and should be chosen deliberately, not
  stumbled into, because it also multiplies the cost by the electorate.
- **`vetkd_public_key` is canister-only.** Verified 2026-07-26 by direct
  ingress call to `aaaaa-aa` on mainnet: `Attempted to call an unsupported
  management canister method`. The frontend cannot fetch the election public
  key itself; it must come through the poll canister. That is fine and
  arguably good -- it puts the key-derivation policy inside attested code --
  but it means the *public key path is application code*, so a client that
  trusts a public key handed to it by an unattested canister has no secrecy.
  The verifier gate (V0) is a prerequisite for V1's secrecy, not just a nice
  ordering.
- **Footgun 1, wrong key id.** Shipping a test key to mainnet is a silent,
  total loss of ballot secrecy -- no error, no warning, just no security. Same
  class as the `CARGO_NET_LOCKED` no-op ic-git caught in
  REPRODUCIBLE_BUILD.md. Assert at deploy time that the key name **is**
  `key_1` on mainnet -- an allowlist, not a denylist of test names. (This
  document previously named `insecure_test_key_1`; the current docs table
  lists only `test_key_1` and `key_1`. Which is exactly why the check must
  assert the good name rather than enumerate bad ones.)
- **Footgun 2, the 10-second timeout.** `vetkd_derive_key` from a canister not
  on the fiduciary subnet is a cross-subnet call and can exceed the replica's
  10s synchronous-call window, returning 202 instead of 200. Diode.io hit this
  in production (reported 2025-07-31; DFINITY confirmed the 10s figure is a
  deliberate tradeoff on 2025-08-04). Mitigation is retry with backoff plus
  polling `read_state`. For a poll canister this lands precisely at close,
  when the decryption path runs and is least tolerant of a hang -- design the
  close path as asynchronous and resumable from the start.
- **Third-party review.** NCC Group's cryptography review of vetKeys was
  published 2025-10-14: **0 critical, 0 high, 0 medium, 2 low, 3
  informational**, all addressed and fix-reviewed. Useful for
  THREAT_MODEL.md's treatment of T-secrecy; it is evidence about the
  primitive, and says nothing about our use of it.

**Threshold ECDSA / Ed25519** -- GA; already used by ic-git for cross-chain
checkpointing. Relevant at V0 for anchoring the final tally hash.

**Certified state / response certification** -- the basis of the bundle
verification; ic-git's `docs/ATTESTATION.md` specifies the certified
module-hash read (BLS12-381 + pinned NNS root key + freshness). **That reader
is the highest-risk unbuilt component in the whole stack and ic-vote depends
on it.** It is the first thing to prototype, in ic-git, not here.

## V0 -- verifiable client, public ballots

**No secrecy at all.** Deliberately.

- A poll canister holding: an eligibility roll, an open ballot box, and a
  tally anyone can recompute from public data.
- Ballots signed by roll-listed identities. Double-voting prevented by
  identity. Everything public.
- The frontend lives in this repo, is pushed to ic-git, served by the git
  canister from the committed bundle, and attested in the ProvenanceRegistry
  as `<repo>#site`.
- The voter-facing verifier reports GREEN/YELLOW/RED per THREAT_MODEL.md
  section 4 before the ballot can be marked.
- Final tally hash checkpointed to the registry, and to Solana once ic-git's
  S1 lands -- two independent trust roots.

**What V0 proves:** the page that took your vote was the reviewed page. That
is the novel claim, and it is provable with zero novel cryptography. Nothing
here needs vetKD, ZK, or a mixnet.

**What V0 is suitable for:** votes that are *already* public -- many board
votes, most shareholder votes, recorded-vote union motions, DAO governance.
That is a real deployable use case, not a toy.

**Dogfooding:** the first real election run on V0 should be a decision about
ic-git itself.

## V1 -- ballot secrecy

- Ballots encrypted client-side under a vetKD-derived key; the canister never
  holds plaintext or a decryption key.
- Threshold decrypt at close, or homomorphic tally without ever decrypting
  individual ballots (preferred where the ballot type allows it -- it removes
  an entire class of "who decrypted early" concern).
- **Re-voting support lands here**, not later: a voter may recast during the
  window, last ballot counts. It interacts with the tally and nullifier design
  and cannot be bolted on afterward. This is the only coercion mitigation with
  a track record (Estonia).
- Bulletin board becomes the public record of encrypted ballots plus proofs.

Open design question: homomorphic vs. mixnet. Homomorphic is simpler and
sufficient for yes/no and single-choice-from-small-slate; mixnets are needed
for ranked or write-in ballots. Start homomorphic and be explicit that ballot
types are restricted.

**Correction surfaced by the 2026-07-26 vetKD check -- read before designing
V1.** The two bullets above are in tension, and the ordering of V1 before V2
partly rests on the tension not existing.

1. **vetKD's IBE does not give you a homomorphic tally.** What the shipped
   libraries provide is: encrypt to an identity, derive that identity's key at
   close, decrypt. Adding ciphertexts is not part of it. An additively
   homomorphic tally needs a separate construction (exponential ElGamal under
   a threshold trustee key); vetKD can protect *that* key, but it is not a
   drop-in substitute for it. "Use vetKD" and "tally homomorphically" are two
   different projects, and only the first is a solved integration.
2. **Decrypt-at-close plus V0's signed ballots is not a secret ballot.** V0
   ballots are signed by roll-listed identities. If V1 keeps that and merely
   encrypts the payload, then at close every ballot is decrypted next to the
   identity that submitted it, and the voter-to-choice link is public the
   moment the election ends. That is *secrecy during voting* -- real, and
   worth something against a live subnet observer or early-tally pressure --
   but it is not what "ballot secrecy" means to a voter.

Which means V1 has to pick one of three, explicitly:

- **(a) Secrecy-until-close, stated honestly.** vetKD IBE, ballots still
  attributable at close. Cheap, shippable, and adequate for votes that are
  already public -- but then it adds little over V0 and should be labeled as
  what it is, not as ballot secrecy.
- **(b) Merge V2 forward.** Anonymous credentials (nullifier) *before* or
  *with* encryption, so decrypt-at-close reveals choices detached from
  identities. This is the honest route to a secret ballot and it makes V1 and
  V2 one rung.
- **(c) Homomorphic tally, never decrypt individual ballots.** Threshold
  exponential ElGamal, vetKD guarding the trustee key. Preserves the V1/V2
  split but is the largest crypto build of the three and restricts ballot
  types hard.

Recommendation: (b). The roadmap's ordering premise -- secrecy is a smaller
step than anonymity -- does not survive contact with what decrypt-at-close
actually reveals. Confirm the homomorphic claim in 1 against
`dfinity/vetkeys` directly before committing; it is reasoning about the
primitive's shape, not a quoted source.

**Upgrade control becomes load-bearing at V1.** The subnet will derive the
election key for whoever the poll canister asks it to. A controller who can
upgrade the canister can therefore add a "derive now" path and read every
ballot before close, and no amount of client attestation sees it. This is
exactly REPRODUCIBLE_BUILD.md's temporal-trust residual, arriving with teeth:
before any election with real secrecy claims, the poll canister's upgrade
path must be under governance or blackholed, and the verifier should surface
the controller set alongside the module hash.

## V2 -- anonymous but eligible

- Roll published as a Merkle root.
- Voter proves in zero knowledge: "I know a leaf in this root, and here is a
  nullifier derived from my key and this election id." Semaphore-shaped.
- Nullifier makes a second ballot from the same member detectable without
  linking either ballot to that member.
- Groth16 verification in a canister is cheap; proving runs client-side in
  wasm. **The prover is a bundle too** -- it goes in the same attested
  frontend, or the anonymity guarantee has an unverified component.

**Eligibility issuance ladder** (T4 in the threat model; pick per deployment,
do not pretend one is universal):

1. **Closed roll** -- organization supplies the member list. V0/V2 default.
   Honest, sufficient for the target market, no new trust root.
2. **Government eID** -- EUDI wallet credentials, BBS+ selective disclosure.
   Real, deployed, jurisdiction-bound.
3. **Passport NFC** -- ZK proof over the ICAO 9303 passive-authentication
   signature (zkPassport / Anon Aadhaar / OpenPassport class). Proves "holds a
   valid passport from country X" without revealing identity. The most
   interesting option and the least mature.

Internet Identity is **not** on this ladder: it gives per-origin pseudonyms,
which is unlinkability, not uniqueness.

## V3 -- coercion mitigation, such as it is

Realistically: re-voting (already in V1), plus UI affordances that make silent
recasting easy and unobservable, plus voter education. We are not shipping
JCJ/Civitas fake credentials -- see THREAT_MODEL.md section 3.

If V3 turns out to be "V1's re-voting plus honest documentation," that is an
acceptable and truthful outcome.

## Dependencies on ic-git

ic-vote cannot ship V0 until ic-git provides:

1. **Certified module-hash reader** (BLS + NNS root key + freshness) --
   `docs/ATTESTATION.md`, unbuilt, highest risk.
2. **Registry `attest()` + K-of-N verifier tooling** -- specified, unbuilt.
   The live Sepolia registry is the `set`/`get` one.
3. **`registry_publish_site` exercised on mainnet** -- shipped, reported
   untested against mainnet.
4. **Multi-chain EVM config** -- currently single-chain (Sepolia); needed to
   put the election's provenance on the chain the organization actually uses.

Items 1 and 2 are the ic-git critical path for this project. Nothing in
ic-vote should start before item 1 has a prototype, because a failure there
changes the whole design.
